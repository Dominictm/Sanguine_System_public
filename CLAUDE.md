# Sanguine System — Инструкции для разработки (VTM Chronicle Manager)

> **Нарративная часть** (роль Рассказчика, правила сцен, литстиль, Scene State JSON) —
> в [`system/narrative_core.md`](system/narrative_core.md). Веб-сервер подмешивает её
> в системные промты генерации; Claude Code этот файл читает только по запросу.

**Активный город** задаётся пользователем. Смотри `cities/<city>/city.md` нужного города или уточни у пользователя.

> ℹ️ Это релизная (тестовая) версия для передачи Рассказчику: города в поставку **не входят**. Создай свой домен через веб-интерфейс (страница «Города» → кнопка «+») или `tools/new_city.js <slug> "<Город>" <год>`, опиши его `city.md` — и он станет активным.

## Структура проекта

**Город** — `cities/<city>/`:

- `city.md` — сеттинг города.
- `rules/` — правила, специфичные для города (если есть).
- `archive/` — `political_state.md` (карта фракций), `events.md` (события города — агрегат из хроник), `timeline.md`, `rumors_elysium.md` / `rumors_dreaming.md` (слухи d20), `characters_index.md` (сводник персонажей), `visitors.md` (персонажи-гости из других городов).
- `characters/<линейка>/<slug>/` — персонажи. Линейки: `vampires`, `fairies`, `mortals`, `werewolves`, `mages`, `hunters`. В папке персонажа: `<slug>.md` (карточка), `<slug>-sheet.md` (V20-лист), `art/` (изображения), `journal/` (дневники `ГГГГ-ММ.md` + `retrospective.md`).
- `locations/<район>/<локация>/` — локации (плоско, без обёртки `district_NN/`; район — формальная сущность с собственной `district.md`, создаётся отдельно от локации, см. `POST /api/cities/:slug/districts`).
- `chronicles/<хроника>/` — `chronicle.md` (спина + финал), `events.md`, `open_threads.md`, `modules/<модуль>/`.

**Глобальное** (одно на все города) — `system/`:

- `rules/` — `npcs_city.md` (протокол НПС), `module_rules.md`, `diary_rules.md`, `literary_style.md` (литературный стиль прозы), `chronicle.md`, листы персонажей по линейкам (`character_sheet_v20.md` — вампиры, `character_sheet_mortal.md` — смертные, `character_sheet_changeling.md` — подменыши/феи; веб-генератор выбирает файл по линейке), `portret.md` (промты изображений), `CHECKLIST.md` (мастер-чеклист).
- `library/` — справочные данные, единый источник истины для сервера и веба: `disciplines/` (17 дисциплин V20, по MD на дисциплину, полные «Литературное описание» + «Система»; API `GET /api/library/disciplines`), `psychics/` (11 психических способностей Numina, аналогично; API `GET /api/library/psychics`), `clans/` / `sects/` (кланы и секты — по MD на запись, без уровней, один блок `## Описание`; API `GET /api/library/clans` / `/sects`; вкладка «Сородичи» — первая вкладка «Библиотеки» в вебе), `relation-types.json` (единый JSON-массив `{slug, name, color, custom}` — базовые 11 видов связей (Сир, Чайлд, Брат, Сестра, Гуль, Домитор, Фамильяр, Союзник, Враг, Семья, Тайная связь); с 2026-08-26 это **эталонный сид**, а не живое хранилище: живой словарь видов связи — документ каждого города `cities/<город>/rules/relation_types.md`, см. «Поле Отношения» выше). Достоинства/недостатки/факты биографии хранятся отдельно (JSON-массивы, не MD-файлы). Все категории «Библиотеки» поддерживают создание/редактирование/удаление авторских записей прямо из веба (канонические защищены от правки — `custom: true`/`false` в записи). Виды связи во вкладках «Библиотеки» не показываются — они городские, редактируются модалкой «Связи» на графе.
- `schema/` — `card_schema.md` (контракт карточки), `validate_cards.js` (линтер).

**Инструменты** — `tools/`. **Веб-интерфейс** — `web/`.

### Карточка персонажа

Обязательные поля (контракт — `system/schema/card_schema.md`): H1 с эмодзи и именем, `Слаг` (= имя папки), `Родной город`, `Линейка WoD`, `Статус`, секция `## 🖼️ Изображения`. Опционально: `Алиасы` (вторая личина/кличка), `Присутствие` (появление в других городах). Имя кириллицей берётся из H1; папка — ASCII-слаг. При упоминании персонажа сверяйся с его карточкой; новых НПС добавляй строго по `system/rules/npcs_city.md`.

**Промт для изображения** (поле `🎨 Промт для генерации изображения`): пишется **на английском**, в трёх блоках (Персонаж → Свет/Атмосфера → Стиль), строго на основе секции `Внешность` карточки персонажа или описания локации. Правила и структура — `system/rules/portret.md`.

**Поле «Отношения»** (2026-08-08, «Связи и отношения»): каждый буллет —
`- [Имя](ссылка) — [Тип] Описание`, где `Тип` — короткий структурированный вид связи
(запись из словаря города или своё слово), `Описание` — опциональное развёрнутое
пояснение. Для связей, синхронизированных как взаимные, перед
`[Тип]` стоит маркер `↔`. Формат и контракт — `system/schema/card_schema.md#Отношения`.
Словарь видов связи — **документ города** `cities/<город>/rules/relation_types.md`
(2026-08-26): две таблицы, «Постоянные» (11 канонических из сида
`system/library/relation-types.json` + добавленные пользователем) и «Авторские»
(заведённые по ходу хроники), колонки `Вид | Слаг | Цвет | Пара | Ключевые слова`.
Порядок строк = приоритет разрешения вида по ключевым словам. Логика —
`web/lib/relation-types.js` (резолвер, пары, авто-регистрация новых видов) и
`web/lib/parsers/relation-types.js` (разбор/сборка документа); API —
`GET/POST/PUT/DELETE /api/cities/:city/relation-types` + `POST …/:slug/promote`
(«сделать постоянной» = перенос строки между разделами).
В веб-интерфейсе управление живёт в модалке «Связи» (кнопка рядом со сбросом графа):
CRUD по обоим разделам, чекбокс «Взаимно» (авто-зеркалирование записи на карточку цели)
и авто-пары по колонке «Пара» (Сир↔Чайлд, Домитор↔Гуль, Брат/Сестра — по полю `Пол`
цели). Ключевые слова и пары правятся только руками в файле. При ручном (не через веб)
редактировании карточки — синхронизацию обратных ссылок делай сам,
см. `system/rules/npcs_city.md`.

## Утилиты (`tools/`)

**Валидаторы:**
- `tools/validate_links.ps1` — проверка всех внутренних ссылок; запускать после переименований/перемещений.
- `system/schema/validate_cards.js` — линтер карточек (поля, статусы, коллизии слагов/алиасов).
- `tools/check_art.ps1 [город]` — сверка ссылок на арт с файлами в `art/`.

**Создание (Node, cities-aware):**
- `tools/new_city.js <slug> "<Город>" <год>` — новый домен (год обязателен, 3–4 цифры; slug задаётся явно — в отличие от веб-формы, выводящей его из названия).
- `tools/new_npc.js <город> <линейка> "<Имя>" …` — карточка персонажа (правит и `characters_index.md`).
- `tools/new_location.js <город> <district> "<Название>" …` — карточка локации.

**Обслуживание:**
- `tools/update_images.ps1 [город]` — синхронизация секций `## 🖼️ Изображения`.
- `tools/build_city_events.js <город>` — пересборка `archive/events.md` из хроник.
- `tools/check_duplicate_names.js [город]` — аудит коллизий отображаемого имени персонажа (без города — проверяет все); ничего не правит, только показывает. Стоит прогнать один раз после обновления через FIX-4b (резолвинг персонажа по slug вместо name, `docs/audit/2026-07-28-fix-plan.md`) — само по себе интерфейс уже не ломает, но подсвечивает случаи, которые могли возникнуть до этого фикса.
- `tools/migrate_char.js`, `tools/close_chronicle.js`, `tools/search.ps1 "запрос"`, `tools/backup.ps1`, `tools/watch.ps1`.

> Создание модуля и дашборд статусов живут в веб-интерфейсе (`web/`): модуль — кнопка «+ Модуль» внутри хроники; статусы — дашборд. Отдельных CLI `new_module.ps1` / `status.ps1` нет.

## Подготовка тестовой / релизной версии

**С 2026-08-30 релиз живёт в отдельном публичном репозитории, не в ветке этого
репозитория.** Раньше релиз был веткой `test` того же (тогда публичного)
репозитория — теперь этот (дев) репозиторий **приватный**, а публично раздаётся
только `Dominictm/Sanguine_System_public` — отдельный GitHub-репозиторий,
содержащий исключительно собранные релизные деревья, без личных данных
городов, без dev-веток и без истории разработки. Причина: GitHub не умеет
скрыть ветку в публичном репозитории от того, кто явно её запросит — спрятать
можно только сам репозиторий целиком, отсюда и разделение на два репозитория.

**Публикация — только через ветку `Releases`, сознательный шлюз.** Разработка идёт
в `master`, `ai_local` и любых других ветках как обычно — сами по себе они
**никогда** не попадают в публичный репозиторий. `Sanguine_System_public`
собирается автоматически только при push именно в ветку `Releases` этого
репозитория — `.github/workflows/release-public.yml` (сработает только на
`refs/heads/Releases`, включая ручной запуск через `workflow_dispatch` — с
любой другой ветки джоб сразу падает с явной ошибкой) запускает
`node tools/build_release.js`, который точечно правит файлы по
`tools/release-overrides.json` (нейтральный «Активный город», пустой `CITY=` в
`start.bat`), вычищает `cities/<город>/` и удаляет пути из `tools/release-exclude.json`
(`.claude`, `.github`, `.vscode`, `.impeccable`, `art-genegic`, `docs/superpowers`,
`docs/design`, `docs/audit`, `web/tests` — дев-окружение и инструменты разработки,
пользователю не нужны), затем форс-пуш результата в `main` **публичного репозитория**
(нужен секрет `RELEASE_REPO_TOKEN` — PAT с правом записи в него, заведённый в
Settings этого репозитория → Secrets and variables → Actions). Ничего не
мёрджится — `main` публичного репозитория каждый раз пересобирается с нуля из
текущего дерева `Releases`, поэтому конфликтов и затирания релизных правок не
бывает. Чтобы выпустить релиз — смержи или запушь готовое состояние в `Releases`;
рутинные коммиты в `master` этого не делают сами по себе.

Ручной запуск (для проверки): `node tools/build_release.js --dry-run` (без записи)
или `node tools/build_release.js --root <папка>` (на отдельной копии). Если правка
меняет один из файлов в `release-overrides.json` так, что find-якорь больше не
совпадает — сборка падает с ошибкой; в этом случае обнови якорь в JSON.

Данные городов в `Releases` (и в `master`) эта пересборка не трогает — там остаётся
рабочая (личная) версия. В корне — единственный `update.bat`, всегда обновляющий релизную
версию из `Sanguine_System_public` (`BRANCH=main`): при обновлении сразу делает
`git reset --hard` без диалога (расхождение истории с пересобранным репозиторием
ожидаемо), а собственные `cities/<город>/` пользователя туда не входят и не
затрагиваются сбросом. Старые локальные копии, у которых `origin` ещё указывает
на прежний `Sanguine_System.git`/ветку `test` (теперь приватный репозиторий) —
`update.bat` при неудаче `fetch` подсказывает команду `git remote set-url origin …`
на новый адрес.

**Если меняется формат файлов городов** (схема карточки, лист персонажа, формат
дневника и т.п. — то, что сделает старые файлы пользователей невалидными или
читающимися иначе) — добавь миграцию в `tools/migrations/` (формат и пример —
`tools/migrations/README.md`). Сервер прогоняет все миграции автоматически при
каждом старте (`web/server.js` → `web/lib/migrations.js`), правя существующие
файлы пользователя под новый формат; ручной запуск — `node tools/run_migrations.js`.

## Веб-интерфейс (`web/`)

При любой работе с фронтендом (`web/public/styles.css`, `web/public/scripts.js`, `web/public/index.html`):

1. **Перед правками** — запусти `/code-review` 
2. **После правок** — прогони impeccable повторно, чтобы убедиться, что изменения не нарушили дизайн-систему (CSS-токены, контрастность, доступность). Для углублённой проверки доступности/UX — скилл **web-design-guidelines**.
3. Новые `font-size` — только через токены `var(--fs-*)`, никаких литеральных `px`.
4. Новые цвета — только через CSS-переменные из `:root`; не добавляй `#hex` вне `:root`.
5. Touch-цели (`button`, `a`, `[role=button]`) — минимум 44px по высоте на `pointer: coarse`.
6. **Проверка в браузере** — используй скилл `run-sanguine-web` (`.claude/skills/run-sanguine-web/`): готовый рецепт перезапуска dev-сервера (`POST /api/restart`) и запуска headless Chrome через сырой CDP (Puppeteer/Playwright в проекте нет), включая обход онбординг-тура и безопасное закрытие инстанса. Не передизайнивай этот процесс с нуля каждый раз.
7. **Приложение обязано работать без интернета.** Никаких CDN и внешних запросов на странице: d3 лежит в `web/public/vendor/`, шрифты Google — в `web/public/fonts/gf/` + `fonts/google-fonts.css`. Сеть — только для ИИ-провайдеров и обновлений.

### Арт и иконки

- **Миниатюры арта** — роут `/city-img-thumb/<путь>?w=640|96` (`web/lib/thumbs.js`): ресайз через PowerShell + `System.Drawing` (`tools/lib/image_resize.js`), кэш в `cities/<город>/.thumbs/` (в `.gitignore`). Исходники арта не трогаются. Сетка персонажей и портреты в узлах графа обязаны ходить через миниатюры, а не за оригиналом на 3 МБ.
- **Иконки линеек** — `web/public/img/system/lineages/<slug>.png`, генератор `tools/generate_lineage_icons.js` + манифест (локальный ComfyUI). В коде — единый хелпер `lineageIconHtml()`; эмодзи из `LINEAGE_ICONS` остались фоллбэком на `onerror`, не удалять. Файлы физически в формате WebP под расширением `.png` (так их отдаёт squoosh, как и остальной арт библиотеки) — браузер определяет формат по содержимому, но `System.Drawing` такие не прочитает.

## Лицензия и правовые ограничения

Проект раздаётся публично по [Dark Pack Agreement](https://www.paradoxinteractive.com/games/world-of-darkness/community/dark-pack-agreement). Из этого следуют **жёсткие ограничения на функциональность**, а не только на тексты:

- **Ничего платного.** Ни платных функций, ни подписок, ни встроенных покупок, ни «донат за ранний доступ». Соглашение требует, чтобы приложение было бесплатным целиком. Пожертвования допустимы, но не могут давать жертвователю ничего, чего нет у остальных.
- **Не воспроизводить книги.** Материалы `system/library/` — краткие пересказы механик своими словами. Не переносить туда текст из изданий; при добавлении механик ссылаться на книгу и страницу.
- **Не убирать атрибуцию.** Логотип Dark Pack и кнопка «О программе» в подвале боковой панели, блок в `README.md` и `NOTICE.md` — условие соглашения, а не украшение.

Код — MIT (`LICENSE`), разбор прав на сторонние ассеты — `NOTICE.md`. План работ по лицензированию и то, что осталось, — `docs/design/2026-08-26-licensing-workplan.md`.

## Делегирование инженерных задач агентам

Для **чисто инженерной** задачи (баг/рефакторинг/тест/фича без роли Рассказчика и
без сеттинга города) — сабагенту через Agent-тул, отдельному worktree или
внешнему/облачному агенту — не давай этот файл целиком. Вместо этого:

1. Заполни [`.claude/AGENT_TASK_TEMPLATE.md`](.claude/AGENT_TASK_TEMPLATE.md) под конкретную задачу.
2. Приложи [`.claude/AGENT_BRIEF.md`](.claude/AGENT_BRIEF.md) — урезанный дев-контракт (стек,
   структура, команды, что нельзя трогать, чек-лист) без нарративной части.

Так агент не тратит контекст на лор/литстиль, которые ему не нужны, и не путает
роль (не начинает писать прозу вместо кода). Для задач, которым нужна роль
Рассказчика/сеттинг города — используй этот файл (`CLAUDE.md`) как обычно,
шаблон не подходит.

## Модули системы (skills)

Каждый модуль веб-интерфейса описан отдельным skill'ом в `.claude/skills/` — ключевые файлы,
формат данных, публичный интерфейс, связанные модули и известные нюансы (в т.ч. где границы
модулей на самом деле проходят иначе, чем кажется по названиям разделов интерфейса). Загружай
только нужный, не весь проект целиком: `dashboard`, `search`, `city-archive` (таймлайн + фракции
+ слухи + визитёры — один роутер), `characters`, `relations-graph`, `locations`,
`chronicles-modules`, `live-session`, `threads`, `audio-library`, `reference-library`,
`dice-roller`, `tools-maintenance`, `backup`, `cities`, `ai-generation`, `file-migrations`.

**Skills обязательно поддерживать в актуальном состоянии.** Любая правка кода, которая меняет
ключевые файлы, публичный интерфейс (роуты/функции), формат данных или связи модуля из таблицы
выше — обновляет соответствующий `SKILL.md` тем же изменением, не откладывая на потом. Новый
модуль (новый роутер, новая вкладка интерфейса, новый самостоятельный клиентский файл) — заводит
новый `.claude/skills/<module-name>/SKILL.md` по тому же шаблону (см. секции ниже) и добавляет
пункт в список выше. Если правка утоньшает границу модуля (переносит роут в другой файл,
расщепляет монолитный роутер на домены и т.п.) — тоже правь «Известные нюансы»/«Ключевые файлы»
сразу, а не оставляй skill ссылаться на файл, которого там уже нет.

**Мастер-чеклист** (новый персонаж / модуль / переименование) — `system/rules/CHECKLIST.md`. Используй вместо поиска по файлам правил.
